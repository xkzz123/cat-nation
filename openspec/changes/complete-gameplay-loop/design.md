# Design：游戏进程衔接与周目生命周期

## Context

地图是原版引擎的操作界面，`bridge` 已包装购买、分工、合成和存档注入；`local-client` 负责保存链、版本冲突和转生提交。现有科技推荐嵌在 `app.js`，高级操作通过原版界面使用。设计在这些入口上补齐流程，保持一份游戏实例。

## Goals / Non-Goals

目标是把“现在做什么、为何受阻、如何处理、完成后去哪”串成可恢复的流程，并使一轮游戏到下一轮可解释、可安全落盘。旧档、自由经营和挑战档均能进入适合的阶段。

本轮不新增资源公式、战斗、剧情结局、自动购买或完整替代高级系统界面。不会把科技研究完毕当作通关，也不会自动转生。地图空间上限的经济调整单独评估。

## Decisions

### Decision 1：由游戏状态推导阶段和行动目标

目的：解决科技目标不能覆盖建设、生产和周目进度的问题，并让旧档直接获得合适目标。

增加 `game/map/progression.js`，以快照输入、只读结果输出实现规则评估。阶段是展示分组，完成状态以原版真实条件计算。可并行发展的信仰、贸易和太空作为分支，不强制排成一条锁死的主线。

| 阶段/分支 | 完成判断方向 | 下一动作示例 |
| --- | --- | --- |
| 营火与供给 | 已有猫薄荷田、基础食物生产 | 采集→田→木材 |
| 聚落与人口 | 已有住房且人口到来 | 等待迁入→安排职业 |
| 科学与分工 | 图书馆、科学来源、日历/农业等实际状态 | 安排学者/农民→研究 |
| 工坊与工业 | 对应科技、设施与材料生产具备 | 工坊→材料合成→生产配套 |
| 高级发展分支 | 按原版系统解锁与完成条件 | 进入贸易、信仰、太空、时间 |
| 周目与挑战 | 原版转生收益/挑战状态 | 查看收益→主动选择是否转生 |

精确 ID 和谓词在第一项实施任务中核对引擎；不新增另一套解锁条件。每项目标包含 `id`、阶段、完成谓词、阻塞结果、动作描述和动作入口。评估返回当前可执行步骤与远期目标；玩家显式追踪科技继续保留，危机提醒独立显示。

备选是继续扩展科技优先级数组，但它无法表达建造和分工的完成条件，因此不采用。无需通用工作流框架。

### Decision 2：拆分正常导航与职责边界

目的：将地图和原版高级系统连成连续旅程，同时保留唯一规则来源。

正常流程为：评估真实状态→显示目标与阻塞→点击动作定位地图/管理面板→玩家执行原版操作→重新评估→展示完成和后续动作。高级操作打开对应原版页并保留返回上下文；返回地图后重新取状态，不凭点击入口认定目标完成。

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| `progression.js` | 目标、阶段、阻塞原因评估 | 不扣资源、不推进模拟、不写经济状态 |
| `map/app.js` 与 shell | 目标卡、危机卡、摘要、导航上下文 | 不计算转生收益，不把 UI 点击当作完成 |
| `map/bridge.js` | 读取引擎、调用既有控制器、原版页定位 | 解锁和可执行性由引擎最终判断 |
| 原版 managers | 经济、研究、挑战、重置与收益 | 目标层不能覆盖原版规则 |
| `local-client.js` | 保存串行化、提交状态、恢复与回归摘要输入 | 冲突或坏档时阻止写入和破坏性操作 |
| `server.mjs` 既有存档服务 | 版本校验、落盘、备份 | 不能仅凭客户端提示认定提交成功 |

原版页定位优先调用其 UI/tab API，需核验具体 manager 和 tab ID；若缺乏可用入口则切入原版并明确所需页签及步骤，不能跳到错误页。未开放的功能显示开放原因，隐藏仅由 feature flag 禁用的内容，避免承诺不可达目标。

### Decision 3：统一阻塞解释，危机提醒独立排序

目的：让玩家能处理当前卡点，同时避免危机覆盖自己选择的长期目标。

目标阻塞按前置未开放、容量不足、地块不适用/已满、投入材料或合成链缺失、岗位/产出缺失、可积累等待的顺序解释。可显示多个缺口，但只突出一项可执行建议。容量与地块是不同阻塞；满图时明确提示现行槽位限制，不把“继续扩地”当成无条件解法。合成建议只展开已解锁配方，检测依赖循环和无法解释的条件，回退到原版说明。

危机卡优先于普通提示，最低覆盖猫薄荷库存、当前净消耗、人口及恢复入口。当前净消耗大于零时，耗尽秒数为库存除以当前实际每秒净消耗，使用当前游戏倍率；暂停时显示模拟已暂停。估计随季节、天气和设施变化更新，只表示当前速率趋势，不预测全年安全。正库存下短期负产出为风险，不宣告已经饥荒；人口归零仍提供恢复供给、住房和等待迁入入口。

恢复后给一次解除反馈，避免每次刷新反复弹出；警报不自动暂停、不自动调岗。保留负产出原始数据便于判断。采用当前趋势估计，先不实现全年季节仿真，以免出现虚假精度。

### Decision 4：转生使用预览、提交、回执的明确状态

目的：让玩家理解本轮收益与损失，并避免失败后重复转生或把未落盘结果当成完成。

预览调用 `getResetPrestige()` 等原版读取方法，展示预计收益、人口与年份、本轮里程碑、主要清空项和保留项；涉及挑战、冷冻舱、时间等特殊保留时使用引擎可核验结果并明确说明条件。预览不得调用 `_resetInternal()` 试算。保留原版确认和挑战 reset hooks，通过统一入口接入既有 `game.reset()` 流程，避免二次扣算或跳过钩子。

提交状态为 `idle → preview → backing-up → resetting → committing → completed`；备份失败进入 `failed-before-reset`，重置后失败进入 `failed-after-reset`；版本冲突进入 `conflict`。提交期间禁止再次确认及其他写入。

1. 等待保存链完成，写入并取得转生前备份回执。
2. 仅执行一次原版重置，固定这次产生的候选存档和本轮摘要。
3. 将候选结果通过现有版本控制保存，收到成功回执后刷新。
4. 新进度包含一次性结算摘要，显示后标记已读，随后展示新周目目标。

失败恢复与正常流程分开：备份失败时保持原进度并允许重试。重置后写入失败时保持暂停，保留同一候选结果和备份引用；先重读磁盘 revision 核验提交是否已成功，成功则继续载入该结果，未成功且版本未变才重试同一候选写入。冲突时不覆盖磁盘，提供重新载入和备份恢复。若现有协议无法识别“已提交但响应丢失”，增加提交标识并以服务端回读核验；不再次执行 `_resetInternal()`。此处必须验证后才能确定是否需要扩展接口。

### Decision 5：只持久化展示元数据，恢复时重算进度

目的：使旧档、导入和回档不会带着与真实游戏不符的阶段完成记录。

新增可选顶层 `progression` 字段，独立于 `hexMap`。v1 包含 `version`、`trackedObjective`、`hidden`（引导收起偏好）、`pendingRunSummary`（摘要 ID、结算数据与已读状态）以及上次会话基线的年份/人口/少量关键资源。经济值始终读取原版数据，不保存“某阶段永久完成”作为真实性来源。重置构造新存档时仅保留引导收起偏好和本次摘要。

存档协议已采用 `operationId`：同一结果及标识重复提交返回原回执，不同结果复用标识或旧版本覆盖新进度均拒绝。客户端通过 `/api/health` 的 `resetProtocol=1` 检查服务支持，再开始转生前备份；断线后回读 `/api/state` 核验结果。挑战开启同样包装原版确认回调，在原版准备钩子之前备份。

旧档缺失字段时从当前真实状态推导，不强迫重做新手动作；未知版本忽略展示元数据且保留经济进度。导入/恢复后丢弃当前内存缓存，按载入文件重建。挑战条件优先于默认推荐，未支持的特殊条件退回挑战原版指引。

回归摘要在原版离线结算完成后生成，展示载入来源、离开时间、当前阶段及关键变化。跨会话资源差额标为“与上次保存相比”，不称为精确离线收益；无基线时只展示当前状态。时钟倒退时不展示负离线时长。摘要不再次调用离线计算，也不按页面速度倍率乘算离线收益。

## Risks / Trade-offs

- 高级系统条件繁多：第一版做入口桥接与代表性里程碑，未知条件明确回退到原版，按阶段存档扩展覆盖。
- 原版 reset 会修改运行状态：重点验证每个失败点；保留现有备份与 revision 约束，禁止盲目自动重跑重置。
- 当前游戏有倍率和有限槽位：估计使用当前速度；空间受阻如实提示，经济平衡变更另提案。
- 新手引导可能打断自由经营：允许跳过与重新打开，完成反馈轻量展示，不强制模态操作。

## Migration Plan

先落地目标评估与 P0 页面，再接入安全转生，最后完成 P1。新字段均可选，读取旧档不改原经济字段；写入沿用同一存档链。回退时关闭新目标展示仍能使用原版与现有地图；若新增提交标识，旧服务端必须显式拒绝不兼容请求，不能静默降级幂等保护。

## Validation Plan

基于真实引擎准备新档、早期科研、工业、太空、可转生和挑战档，验证目标条件、阻塞、挑战覆盖、恢复旧档和重置后的目标。浏览器验收覆盖新档首次过冬、工业配套、原版高级页往返、转生结算、新周目与离线回来。失败注入覆盖备份失败、重置后提交失败、响应丢失和版本冲突；检查磁盘与内存状态、备份可恢复性以及重置仅执行一次。

## Open Questions

产品侧待审阅的是 P0/P1 优先级、原版桥接的第一期范围和阶段名称。工程侧的 tab API、挑战特殊条件、提交回读能力与精确目标谓词由实施前核验任务解决，不以猜测写入规则。
